# Engineering KPI for AI-Native Development

## Measurement Rules

These KPIs are measurement definitions, not current results. No current KPI value is reported because the repository does not contain a complete historical dataset for all measures.

Use only evidence that can be obtained from:

- Repository files, test reports, and traceability documents.
- GitHub Pull Request metadata and review events.
- GitHub Actions workflow runs, jobs, and logs.
- GitHub Issues and linked work-order/RCA records.

For every rate, report the numerator, denominator, time window, and any excluded runs. If the denominator is zero, report `N/A`, not zero percent.

## KPI Definitions

### KPI-01 — Automated Test Pass Rate

- **Definition:** Percentage of executed automated test cases that pass in a defined measurement window.
- **Formula:** `passed tests / executed tests * 100`.
- **Data source:** Maven Surefire reports from `mvn clean test`, GitHub Actions test logs, or retained CI test artifacts.
- **Measurement frequency:** Per CI run, aggregated weekly or per release.
- **Why it matters:** Shows whether the automated test harness provides a reliable verification signal.
- **Limitation:** A passing test only proves the scenarios it covers; it does not prove complete requirements or security coverage. Test discovery/configuration errors can also make a pass rate misleading.

### KPI-02 — CI Pass/Fail Rate

- **Definition:** Percentage of completed GitHub Actions CI workflow runs that pass, with failed runs reported separately.
- **Formula:** `successful CI runs / completed CI runs * 100`; also report `failed CI runs / completed CI runs * 100`.
- **Data source:** GitHub Actions workflow run history for `.github/workflows/ci.yml`, including job conclusions.
- **Measurement frequency:** Per workflow run, aggregated weekly or monthly.
- **Why it matters:** Measures the stability of the shared integration and quality gate.
- **Limitation:** A CI pass does not distinguish a healthy product from weak tests. Retries, cancelled runs, infrastructure failures, and duplicate runs must be classified consistently.

### KPI-03 — PR Cycle Time

- **Definition:** Elapsed time from Pull Request creation to merge or closure.
- **Formula:** `merged_at - created_at` for merged PRs; report closed-unmerged PRs separately.
- **Data source:** GitHub Pull Request timestamps and state history.
- **Measurement frequency:** Per PR, aggregated monthly or per work order.
- **Why it matters:** Shows delivery flow efficiency from proposed change to integrated change.
- **Limitation:** Waiting time outside engineering control, holidays, draft PRs, dependency queues, and large or multi-scope PRs can distort comparisons.

### KPI-04 — PR Review Time

- **Definition:** Elapsed time from a PR being ready for review to the first substantive human review, and optionally to final approval.
- **Formula:** `first human review timestamp - ready_for_review timestamp`; optionally `approval timestamp - ready_for_review timestamp`.
- **Data source:** GitHub PR timeline, review events, draft/ready transitions, and reviewer identity.
- **Measurement frequency:** Per PR, aggregated weekly or monthly.
- **Why it matters:** Measures whether human control happens promptly after AI-assisted or conventional changes are proposed.
- **Limitation:** GitHub event history may not distinguish substantive review from a comment or automated action. Reviewer time zones and draft periods affect the result.

### KPI-05 — Requirement-to-Test Traceability

- **Definition:** Percentage of in-scope requirements with at least one linked test scenario and an identified automated test or an explicitly recorded gap.
- **Formula:** `requirements with traceable scenario and test/gap status / in-scope requirements reviewed * 100`.
- **Data source:** `test-design.md`, source requirement documents, test method names, and test reports.
- **Measurement frequency:** Per work order or requirement change; recheck before merge and release.
- **Why it matters:** Prevents AI-generated tests from being mistaken for complete requirement verification.
- **Limitation:** Traceability based on documentation and test names requires human review. A linked test may still assert the wrong behavior, and a requirement may be too broad for a single binary mapping.

### KPI-06 — Automated Test Coverage

- **Definition:** Measured coverage of production code or requirements by automated tests, using the selected coverage model.
- **Formula:** For code coverage, `covered executable instructions or branches / total executable instructions or branches * 100`; for requirement coverage, use KPI-05's traceability formula.
- **Data source:** A retained coverage report generated by an approved CI tool, plus `test-design.md` for requirement coverage.
- **Measurement frequency:** Per CI run and release.
- **Why it matters:** Identifies untested code paths and prevents relying only on test count.
- **Limitation:** The current workflow does not configure a coverage tool, so no current code-coverage value can be reported. Coverage percentage does not measure assertion quality, security, or business relevance.

### KPI-07 — Escaped Defects

- **Definition:** Number or rate of defects found after merge or release that should reasonably have been detected by the pre-merge test/review process.
- **Formula:** Count escaped defects in the period; optionally `escaped defects / merged PRs * 100` or `escaped defects / released changes * 100`.
- **Data source:** GitHub Issues, incident records, bug labels, links to the introducing PR/commit, and release verification records.
- **Measurement frequency:** Per incident and aggregated monthly or per release.
- **Why it matters:** Tests the real effectiveness of the quality gates rather than only their pass rate.
- **Limitation:** Requires consistent defect classification and reliable links to the introducing change. The repository does not contain enough incident history to report a current value.

### KPI-08 — AI-Assisted Changes Reviewed by Humans

- **Definition:** Percentage of AI-assisted PRs with an identifiable human review before merge.
- **Formula:** `AI-assisted PRs with human approval before merge / AI-assisted PRs merged * 100`.
- **Data source:** GitHub PR reviews, PR metadata/labels, review checklist evidence, and `../06-quality-security/ai-human-review.md`.
- **Measurement frequency:** Per merged PR, aggregated monthly.
- **Why it matters:** Measures whether AI assistance remains human-controlled rather than becoming an implicit approval mechanism.
- **Limitation:** GitHub does not inherently identify AI-assisted work. A reliable measure requires an agreed PR label, checklist field, or work-order record. The governance document alone is not historical evidence.

### KPI-09 — Failed CI Caused by Test/Code Changes

- **Definition:** Percentage of failed CI runs where the primary cause is a test, production-code, build, or configuration change in the associated PR rather than runner/infrastructure failure.
- **Formula:** `failed CI runs attributed to repository changes / all failed CI runs * 100`.
- **Data source:** GitHub Actions failed logs, changed-files view, PR metadata, Maven/Surefire reports, and failure classification.
- **Measurement frequency:** Per failed run, reviewed weekly and aggregated monthly.
- **Why it matters:** Distinguishes useful quality-gate detection from flaky or infrastructure-related failure.
- **Limitation:** Cause attribution requires human classification when logs do not identify a single cause. A failed run may have multiple contributing changes.

### KPI-10 — RCA Completion

- **Definition:** Percentage of qualifying CI failures or escaped defects with a completed, reviewed root-cause analysis record.
- **Formula:** `qualifying incidents with completed RCA / qualifying incidents due for RCA * 100`.
- **Data source:** GitHub Issues, linked PRs, incident/RCA documents, labels, and closure status.
- **Measurement frequency:** Per incident; aggregate monthly or per release.
- **Why it matters:** Converts failures into repeatable engineering learning and reduces recurrence.
- **Limitation:** The repository does not define a mandatory RCA template or a complete incident dataset. “Completed” must be defined by the team before the KPI is used.

| KPI-09 | Failed CI logs plus changed files | WO-401 documents one intentional failure; this is not a historical rate dataset. |
| KPI-10 | RCA records and issue closure | No mandatory RCA record or complete incident history is present. |

## Reporting Constraints

- Do not report a current value when the required GitHub, CI, issue, or release evidence has not been collected.
- Do not treat test count as test quality or requirement coverage.
- Do not treat CI pass rate as proof that security and business behavior are correct.
- Keep intentional test failures separate from unintentional product failures when calculating KPI-09.
- Record the measurement window and evidence links with every published KPI result.
